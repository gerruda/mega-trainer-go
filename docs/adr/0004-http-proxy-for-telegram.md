# ADR-0004. HTTP(S)-прокси для Telegram Bot API

**Статус:** принято
**Дата:** 2026-10-28

## Контекст

`api.telegram.org` недоступен напрямую в России. Без прокси бот падал на
`getMe` с `connection refused` и не мог стартовать. Прокси у пользователя —
локальный HTTP-прокси (`http://127.0.0.1:12334`).

## Решение

- Новый пакет `internal/telegramapi` собирает `http.Client` с
  `http.Transport.Proxy`, если задан `telegram.proxy_url`.
- Настройка приходит из конфига/окружения (`TELEGRAM_PROXY_URL`), не хардкодится.
- Поддерживаются только схемы `http://` и `https://`.
- Клиент Bot API создаётся через `NewBotAPIWithClient`, таймаут запросов — 60 с.
- При старте удаляется webhook: при активном webhook Telegram отвечает
  `409 Conflict` на `getUpdates`, и бот выглядит «живым, но молчащим».
- В лог попадает только host прокси (креденшелы маскируются); в текст ошибки
  авторизации добавляется подсказка про `TELEGRAM_PROXY_URL`.

## Рассмотренные альтернативы

| Вариант | Почему нет |
|---|---|
| SOCKS5 (`golang.org/x/net/proxy`) | нужна лишняя зависимость; HTTP CONNECT-прокси достаточно для HTTPS API |
| `HTTP_PROXY` из окружения | неявно и конфликтует с остальным HTTP-трафиком; лучше явный конфиг |
| Собственный reverse-proxy | усложняет деплой без выгоды для одного бота |

## Последствия

- Бот работает в сетях с блокировкой Telegram; переключение — одна переменная.
- В Docker `127.0.0.1` указывает на контейнер: нужен `host.docker.internal`
  или запуск бота на хосте (описано в README/OPERATIONS).
- Прокси-транспорт покрыт юнит-тестами (включая отказ от socks5 и маскирование).
