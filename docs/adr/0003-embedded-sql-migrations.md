# ADR-0003. SQL-миграции, встроенные в бинарник

**Статус:** принято
**Дата:** 2026-10-28

## Контекст

В исходной версии существовали два конкурирующих механизма миграций: SQL-файл
с секцией `-- down` в том же файле и захардкоженный список `Migration` в
`internal/storage/postgres/migration.go`. Схемы `users` в них не совпадали,
а файл с `DROP TABLE` в конце был опасен при выполнении через `psql`.

## Решение

- Единственный источник схемы — `migrations/NNNN_name.sql` (+ `.down.sql`).
- Файлы встроены в бинарник через `//go:embed` (`migrations/embed.go`).
- Раннер `postgres.Migrator`:
  - таблица `schema_migrations (version, applied_at)`;
  - `pg_advisory_lock` — защита от параллельного запуска;
  - каждая миграция — в транзакции;
  - команды `up`, `down`, `status` (`cmd/migrate`).
- В Docker миграции применяет отдельный сервис `migrate` до старта бота;
  в systemd — `ExecStartPre=migrate up`.

## Рассмотренные альтернативы

| Вариант | Почему нет |
|---|---|
| `golang-migrate` / `goose` | ещё одна зависимость; текущий объём миграций не оправдывает |
| Миграции во время старта бота | смешивает роли процессов и мешает горизонтальному масштабированию |
| Только SQL-файлы без раннера | нет учёта применённых версий и откатов |

## Последствия

- Бинарник всегда несёт схему, соответствующую коду — нет расхождения версий.
- Деплой: `migrate up` идемпотентен, повторный запуск безопасен.
- Откат — только последней миграции (`down`), это осознанное ограничение.
